# Architecture Decision: Runtime Output Directory Structure

**Date**: October 15, 2025  
**Status**: ✅ IMPLEMENTED  
**Affects**: Scaffolding, Phase Orchestrators, All Generated Projects

## Executive Summary

Phase orchestrators create runtime output files (rendered templates, environment files, snapshots, logs, etc.). These outputs are **runtime artifacts** that should be separate from source code to:
- Prevent git conflicts with source directories
- Make `.gitignore` rules clearer
- Explicitly distinguish code from data
- Allow runtime cleanup without affecting source

## Decision

**All phase orchestrators use a dedicated `runtime/` directory for outputs**, not `phases/`.

### Directory Structure

```
project-root/
├── src/                           ← Source code
│   └── phases/                    ← Phase orchestrators (Python code)
│       ├── phase_1_preflight/
│       │   ├── __init__.py
│       │   └── orchestrator_*.py
│       ├── phase_2_template_rendering/
│       └── ...
│
└── runtime/                       ← Runtime outputs (gitignored)
    ├── phase_1_preflight/
    │   └── outputs/
    │       └── validation_report.json
    ├── phase_2_template_rendering/
    │   └── outputs/
    │       ├── Caddyfile
    │       └── docker-compose.override.yml
    ├── phase_3_snapshot/
    │   └── outputs/
    │       ├── snapshots/
    │       │   └── snap_*.json
    │       └── config_backup_*/
    └── phase_4_deployment/
        └── outputs/
            └── .env.development
```

## Implementation

### 1. Phase Orchestrator Pattern

All phase orchestrators follow this pattern:

```python
class PhaseOrchestrator:
    def __init__(self, project_root: Path, config: Dict[str, Any]):
        self.project_root = project_root
        self.config = config
        
        # Runtime directory for this phase
        self.phase_dir = project_root / "runtime" / f"phase_{N}_{phase_name}"
        self.outputs_dir = self.phase_dir / "outputs"
        
        # Ensure outputs directory exists
        self.outputs_dir.mkdir(parents=True, exist_ok=True)
```

### 2. Scaffolding Template

The control-flow scaffolder (`scaffolder.py`) generates orchestrators with the `runtime/` pattern:

```python
# From scaffolder.py line 274:
self.phase_dir = project_root / "runtime" / f"phase_{phase.sequence}_{phase.phase_id}"
self.outputs_dir = self.phase_dir / "outputs"
```

### 3. .gitignore Configuration

Projects using this pattern should include:

```gitignore
# Runtime output directories (auto-generated by phase orchestrators)
/runtime/
/phases/        # Legacy - in case old outputs exist

# Python
__pycache__/
*.py[cod]
```

## Rationale

### Why `runtime/` instead of `phases/`?

| Issue | Problem with `phases/` | Solution with `runtime/` |
|-------|----------------------|--------------------------|
| **Naming collision** | `src/phases/` (code) vs `phases/` (outputs) causes confusion | Clear separation: `src/` is code, `runtime/` is data |
| **Git confusion** | Which `phases/` directory should be in `.gitignore`? | `runtime/` is obviously ephemeral |
| **Cleanup** | Hard to clean outputs without deleting source | `rm -rf runtime/` is safe |
| **Semantics** | "phases" doesn't indicate temporary data | "runtime" clearly means "generated at runtime" |

### Alternative Considered: `outputs/`

We considered `project_root / "outputs" / "phase_X"` but rejected it because:
- Less descriptive than "runtime"
- Doesn't emphasize the ephemeral nature
- "outputs" could be confused with permanent artifacts

### Alternative Considered: `src/phases/phase_X/outputs/`

Keeping outputs with source was rejected because:
- Mixes code and runtime data in version control
- Makes `.gitignore` rules complex (`src/phases/*/outputs/`)
- Harder to clean all outputs at once
- IDE tools may index output files unnecessarily

## Migration Path

### For Existing Projects

If you have an existing project with outputs in `phases/`:

1. **Move outputs** to `runtime/`:
   ```bash
   mv phases runtime
   ```

2. **Update orchestrators**:
   ```python
   # Old:
   self.phase_dir = project_root / "phases" / "phase_X"
   
   # New:
   self.phase_dir = project_root / "runtime" / "phase_X"
   ```

3. **Update .gitignore**:
   ```gitignore
   /runtime/
   /phases/    # Keep for safety during transition
   ```

4. **Test**:
   ```bash
   python test_integration_full.py
   # Verify outputs appear in runtime/ not phases/
   ```

### For New Projects

New projects scaffolded with control-flow v2.0+ automatically use `runtime/`.

## FAQ

### Q: Can I use a different directory name?

Yes, but you'll need to:
1. Override in your orchestrator's `__init__`
2. Update `.gitignore`
3. Document the decision for your team

### Q: Should runtime/ be in version control?

**No**. The `runtime/` directory is for ephemeral data created during execution. It should be in `.gitignore`.

### Q: What about persistent artifacts like snapshots?

Snapshots are **runtime artifacts** for disaster recovery, not source code. They belong in `runtime/`. If you need long-term backup:
1. Keep snapshots in `runtime/` for immediate rollback
2. Copy critical snapshots to a backup system
3. Don't commit them to git

### Q: How do I clean runtime outputs?

```bash
# Clean all runtime outputs
rm -rf runtime/

# Clean specific phase outputs
rm -rf runtime/phase_3_snapshot/outputs/snapshots/*

# Clean old snapshots (keep last 10)
ls -t runtime/phase_3_snapshot/outputs/snapshots/*.json | tail -n +11 | xargs rm -f
```

### Q: Does this affect the transformation system?

No. The transformation system operates on:
- YAML specs (`control_flows.yml`)
- Source code directories (`src/phases/`)

It doesn't touch `runtime/` directories.
